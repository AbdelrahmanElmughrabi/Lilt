## Findings and decisions

### R03-F01 — refresh the Python/OpenSSL/Expat runtime before final build

**Required remediation or a reviewed, component-specific disposition; no app compromise demonstrated.** OpenSSL 3.5.8 falls within the affected 3.5 series addressed by the [29 September vendor advisory](https://openssl-library.org/news/secadv/20260929.txt). In particular, **CVE-2026-35189 (Low)** concerns certificate-extension memory pressure in TLS clients as well as servers. `backend/models.py` uses Python HTTPS for fixed model-download endpoints. Fixed URLs, certificate verification and model hashes reduce exposure but do not replace a TLS parser patch. Upgrade to a trusted compatible runtime with **OpenSSL 3.5.9 or a later supported fix**, then verify its actual bytes/version and download/offline/error behavior.

The advisory's High DTLS finding is not evidence of a High-severity Violilt path: no app-authored DTLS/QUIC/server-SSL/CMP/SM2 flow was found. Do not transfer the bulletin's highest severity to this application automatically.

[Python 3.12.15](https://www.python.org/downloads/release/python-31215/) is a later security release. Its fixes cover SSL context/argument handling, credential-manager scheme matching, archive handling and other stdlib behavior. This app does not configure a password manager or SSL server; imported documents are not extracted as arbitrary tar archives. Approved voice/model bytes are verified before inference/loading. Those limits do not prove all transitive stdlib paths safe. A patched runtime is preferable to carrying unreviewed exceptions. Python 3.12 security releases are source-only from python.org; do not assume an official Windows installer exists or silently move to an incompatible Python ABI.

[Expat's upstream changelog](https://github.com/libexpat/libexpat/blob/master/expat/Changes) records security fixes after 2.8.3, including 2.8.4's quadratic parsing fixes and 2.8.5's malformed UTF-16 fix. pypdf imports an XMP/Expat path, but the application's selectable-text workflow does not request XMP; the benign PDF probe confirmed that one case. Markdown uses HTMLParser, not Expat. No hostile XML app path was demonstrated. Select a patched compatible runtime with a current Expat and verify the relevant call sites; upgrading only OpenSSL does not close the interpreter/Expat findings.

The upstream CPython tag's Windows external-library defaults do not match this supplied runtime's observed library versions. They cannot establish its exact build provenance. Preserve R-01/R-02's environment while evaluating a separately authorized isolated runtime; retain NVIDIA/cp312 compatibility or deliberately revalidate all affected wheels if the ABI changes.

### R03-F02 — constrain stored/imported audio parsing and resolve native audio coverage

**Required focused follow-up before release; exploitability on the actual Windows x64 build is unverified.** SoundFile 0.13.1's libsndfile DLL reports 1.2.2 and matches the older payload byte-for-byte. The native file includes static markers for FLAC 1.4.3 and Opus 1.5.2. Exact remaining codec/build/patch provenance is not established by those markers.

`backend/cache.py:audio_info` calls `sf.info()` before checking frames/channels/rate/subtype; libsndfile therefore parses the input before the app rejects an unsupported format. A valid AIFF renamed `.wav` passes that helper's checks. Saved-library imports/recovery/resume can involve files that were not freshly produced by the running worker. A `.wav` filename and post-parse PCM check are insufficient to rule out native parser exposure.

Primary reports require nuanced treatment:

| Report | Disposition for this batch |
| --- | --- |
| [CVE-2026-37555 CNA record](https://cveawg.mitre.org/api/cve/CVE-2026-37555), [upstream reference](https://github.com/libsndfile/libsndfile/issues/833) | Reported IMA ADPCM WAV integer overflow; a WAV parser path matters even though the app only intends PCM16. No reproduction or exact-binary patch verification performed; retain as unresolved, not a proven heap exploit. |
| [CVE-2026-88372 CNA record](https://cveawg.mitre.org/api/cve/CVE-2026-88372), [upstream issue 1151](https://github.com/libsndfile/libsndfile/issues/1151) | MAT4 integer-overflow report, with [proposed upstream fix](https://github.com/libsndfile/libsndfile/pull/1167). Generic autodetection means the format cannot be dismissed solely by extension. No malicious MAT4 was opened. |
| [CVE-2026-88386 / upstream issue 1150](https://github.com/libsndfile/libsndfile/issues/1150) | Misaligned access report explicitly distinguishes strict-alignment/sanitizer builds from x86, where it can work. No demonstrated Windows x64 crash; do not count as a confirmed app DoS. |
| [CVE-2024-50613 / issue 1034](https://github.com/libsndfile/libsndfile/issues/1034), [CVE-2025-56226 / issue 1089](https://github.com/libsndfile/libsndfile/issues/1089) | MPEG encoding paths. Violilt generates PCM16 WAV, not MPEG; no affected normal encoding path established. |
| [Upstream issue 1118](https://github.com/libsndfile/libsndfile/issues/1118) | Reports a malformed WAV INFO chunk hang. Another reason to assess bounded validation before native opening; no hang probe was run here. |

Recommended source follow-up: trace every stored/cache/imported WAV read, then plan bounded strict PCM16 RIFF validation or use the standard-library WAV reader for these reads, preserving mono/24-kHz samples, durations and timeline behavior. Reject unsupported containers/compression **before** libsndfile autodetection. Evaluate a maintained patched audio build where needed and preserve its replacement/source obligations (R-04). A header check alone is not a complete sandbox or proof of safe native decoding. Keep original files/recovery non-destructive; test malformed/truncated/renamed inputs, resume/cache/assembly/playback and real CPU/CUDA after a fix. No source change or dependency installation was made in this audit.

### R03-F03 — DOMPurify advisory feed gap; update recommended, affected modes not enabled

**Maintainer version-range matches, Low; no demonstrated current-config bypass.** Locked/installed DOMPurify **3.4.16** is covered by three 12 October advisories, all listing **3.4.17** as patched:

- [GHSA-c6gr-qvv4-5v3f](https://github.com/cure53/DOMPurify/security/advisories/GHSA-c6gr-qvv4-5v3f): XHTML parser mode plus allowed SVG animation attributes.
- [GHSA-mrv2-3pqr-j5jr](https://github.com/cure53/DOMPurify/security/advisories/GHSA-mrv2-3pqr-j5jr): in-place sanitization with node-removing hooks.
- [GHSA-cg2g-xh64-v4q7](https://github.com/cure53/DOMPurify/security/advisories/GHSA-cg2g-xh64-v4q7): template sanitization with DOM output/shadow content.

App.svelte uses a string input/output, a narrow HTML tag list and **no allowed attributes**, with none of those modes/hooks. Source tracing plus the four-input browser probe supports non-applicability of those configurations for current use; it does not prove the whole app is XSS-free. Recommend a separate authorized lock/install/build update to at least 3.4.17, retaining the restrictive configuration and revalidating Markdown/editor/native behavior. This would change R-01/R-02 assets/dependencies, so coordinate the new snapshot first. The empty OSV/npm responses must be reported alongside these maintainer advisories.

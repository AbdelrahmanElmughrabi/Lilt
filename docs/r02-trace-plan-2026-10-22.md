## Proposed sequence and acceptance

### R-02A — targeted storage fault reproductions first

Use new disposable fixture folders and injected `sqlite3.OperationalError`/`OSError`/partial-copy failures at specific boundaries. Never fill the real disk, change system ACLs or corrupt any real library. Record pre/post bytes and the difference between injected conditions and physical OS failures.

1. **Listener and shutdown:** inject one persistence failure during job progress, terminal events, benchmark completion and close. Observe listener liveness, active/operation state, last durable checkpoint, cancellation/worker cleanup and a subsequent successful job after storage recovers. Cleanup must not depend on successful persistence; never claim an uncommitted update was saved. Avoid broad `except: pass`, busy retry loops and unbounded error-state accumulation.
2. **Export preservation:** approve replacement of a synthetic existing export, fail after a partial write, and verify both the prior destination and source recording. If reproduced, plan a same-directory temporary copy followed by replacement only after successful copying, with cleanup of only the owned temporary file. Retain successful export, extension and confirmation behavior.
3. **Combined failure classification:** bad JSON plus unavailable quarantine storage; unreadable whole-file database; job/cache directory creation, section publication, cache write/prune, final recording assembly and cancellation during failure. Determine which paths already fail safely and which actually need changes. Minimum acceptance is preserved originals/healthy data/completed sections, truthful recoverable state and usable retry; no automatic destructive repair.

After reproduction, implement only confirmed failures in small separately reviewable batches, with targeted regressions and relevant existing tests. Source changes are not authorized by this planning request. Before modifying inputs shared with R-01 review, finish/coordinate that review snapshot; do not silently invalidate its test inputs.

### R-02B — classify the navigation timeout

Use a fresh synthetic library and a controlled second loopback origin. Compare JS `location.href`/assign/replace and native/CDP navigation, plus frame attempts. Capture native navigation events, cancellation/status, native `CoreWebView2.Source`, document identity/readiness/DOM, a bounded fresh API call, the previous API reference and an actual UI action. Gather native state even when Playwright's body locator fails; keep all waits bounded and retain failed observations.

Acceptance: the foreign page receives no app bridge/data; canceled navigation preserves or safely recovers usable app UI/bridge. Distinguish a visible blank/stuck window from an instrumentation/target-state failure. Include the R-01 close behavior after the attempted navigation and report any overlap to the verification chat through the publisher. Do not change CSP/origin rules or reload away unsaved edits to hide the symptom. A confirmed failure gets its own minimal fix plan; a harness-only problem gets corrected evidence.

### R-02C — local-resource threat check and decision

Recheck current-source synthetic media with app-origin playback/streaming/HEAD/Range, unknown IDs, traversal/Host rejection and controlled foreign-origin fetch/media/frame attempts. Explicitly separate raw local known-ID access from browser-readable disclosure. Check whether any ordinary flow discloses IDs/credentials to an untrusted origin. Preserve playback/seek behavior.

If browser isolation still holds and the only remaining access assumes a local client already knows the UUID, record the residual risk and recommend whether session binding is justified. No session-token feature is implied by this plan. Keep Windows cross-user/installed ACL assertions open until synthetic installed-package testing is available; do not inspect personal AppData permissions.

### R-02D — evidence handoff to installed testing

Map standard-user package/data permissions, package immutability, runtime path/DLL behavior and interruption/recovery cases into R-08/R-09/R-10. Testing the final installer on another machine stays mandatory. A source fault-injection pass cannot close these installed/hardware gates.
